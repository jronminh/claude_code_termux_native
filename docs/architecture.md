# Architecture

A file-by-file map of this repo, for contributors and for Claude itself.
Staged to `~/.claude/claude-native/docs/architecture.md` by `install.sh`
(unconditionally, like the scripts under `scripts/`) so this detail is
available on-device without needing the repo checkout, and without
costing any tokens in `~/.claude/CLAUDE.md` unless actually read — see
"Why this lives here, not in CLAUDE.md" at the bottom.

**Not scripture** — if this disagrees with the actual code, the code
wins. Re-check before relying on a specific claim here after any real
change to the scripts it describes.

## Top-level entry points

- `install.sh` — the installer. Idempotent, flag-gated opt-ins:
  `--with-notifications`, `--with-adb-bridge` (combinable) — but these
  only matter at FIRST install; toggling either one later is
  `termux-claude-features`'s job (below), not install.sh's.
- `uninstall.sh` — reverses everything install.sh does, unconditionally
  (always attempts removal of every opt-in feature, no flags needed to
  mirror what was installed). `--full` also wipes the cached ~300MB
  binary. For turning off ONE feature without the full teardown, that's
  `termux-claude-features disable <feature>`, not this.
- `migrate.sh` — one-time bridge for users still on the old pre-v2.1.113
  plain-npm install; detects it, backs it aside, hands off to install.sh.
- `bootstrap.sh` — the `curl | bash` remote entry point (git clone/cd/
  install.sh in one step). Forwards its own args to install.sh, so
  `bootstrap.sh | bash -s -- --with-adb-bridge` works.

## `scripts/` — staged to `~/.claude/claude-native/` (mostly), or installed to `$PREFIX/bin`

Staged to `~/.claude/claude-native/*.sh` (run in-place from there, not from
the repo, once installed):

- `lib.sh` — **install/uninstall-only helpers, sourced by
  install.sh/uninstall.sh/migrate.sh, never staged or run standalone.**
  `claude_md_upsert`/`_remove`, `keybindings_upsert`/`_remove`,
  `step`/`step_banner` (the `[n/N] ... ok` progress UI), `check_platform`,
  `kernel_is_risky`/`epoll_fix_present`, plus the core (non-toggleable)
  `DOCTOR_HOOK_MARKER`/`doctor_hook_command`. It also sources
  `feature-hooks.sh` (below) from the repo, so install.sh/uninstall.sh get
  the toggleable-feature functions transitively.
- `feature-hooks.sh` — **the single source of truth for every toggleable
  feature** (currently `notifications`, `adb-bridge`): `*_HOOK_MARKER`
  constants, `*_hook_command()` generators, the generic
  `hook_upsert_entry`/`hook_remove` (marker-based settings.json editing —
  add/remove one hook entry without touching anyone else's), and per-
  feature `enable_X`/`disable_X`/`X_wired`. Unlike `lib.sh`, this file IS
  staged (`~/.claude/claude-native/feature-hooks.sh`) because it's sourced
  from TWO places: `lib.sh` (repo copy, install/uninstall time) AND
  `claude-features.sh` (staged copy, runtime — see below). **Read this
  file, not install.sh/uninstall.sh, to see how a feature actually gets
  wired/unwired** — install.sh/uninstall.sh are thin callers into it.
- `claude-features.sh` — backs the `termux-claude-features` command
  (`status`/`enable <feature>`/`disable <feature>`). Sources the STAGED
  `feature-hooks.sh`. Lets a feature be toggled long after install without
  re-running install.sh or reaching for uninstall.sh. `cmd_status` carries
  each feature's one-line description AND safety notes directly in its
  own output — that text lives here, nowhere else (see "core pattern"
  below and "Why this lives here, not in CLAUDE.md").
- `autocheck.sh` — sourced from `~/.bashrc` every interactive shell.
  Silent self-heal (chmod/re-patch/re-add DISABLE_AUTOUPDATER) then
  `update.sh --check-only`. Does NOT run inside a Claude-spawned Bash-tool
  shell (non-interactive, doesn't read `.bashrc`).
- `update.sh` — the real download/verify/patch/install pipeline.
  `--check-only` (silent unless a new version exists) vs. no-flag (does
  the work). Also does rollback bookkeeping (`claude.prev`).
- `doctor.sh` — the one-shot diagnostic dump. `--json` / `--fix`. THE
  place status lines for every feature (core + every opt-in one) live —
  when adding a new feature, add its status line here too.
- `session-hooks.sh` — opt-in (`notifications`). `submit`/`stop`/`notify`
  subcommands wired to `UserPromptSubmit`/`Stop`/`Notification`. Wake-lock
  ref-counting across concurrent Termux tabs, battery-aware context
  injection, "task finished" notification.
- `adb-bridge.sh` — opt-in (`adb-bridge`), but ALWAYS staged regardless
  (like `session-hooks.sh` — staging alone is inert).
  `status`/`screenshot`/`dump`/`tap`/`swipe`/`logcat`/`logcat-clear`/`nag`.
  `nag` is what the opt-in Stop hook calls; never fails, exits 0 always.
- `claude-job-runner.sh` — invoked by Android's real JobScheduler via a
  per-job stub script (`jobs/<name>.sh`, generated by `claude-job.sh add`).

Installed to `$PREFIX/bin/` (these ARE what the user types):

- `claude-wrapper.sh` → `$PREFIX/bin/claude` — the actual wrapper Termux
  runs. Every line here works around one specific Bionic/glibc conflict;
  see `skills/termux-doctor/SKILL.md`'s trap list before touching it.
- `claude-job.sh` → `$PREFIX/bin/termux-claude-job` — add/list/remove/run/
  log subcommands for scheduled jobs.
- `termux-update-claude.sh` → `$PREFIX/bin/termux-update-claude` — thin
  `exec` wrapper around the staged `update.sh`.
- `termux-claude-features.sh` → `$PREFIX/bin/termux-claude-features` —
  thin `exec` wrapper around the staged `claude-features.sh`. Always
  installed (not gated by either `--with-X` flag) — it's the OFF switch
  too, so it can't itself be opt-in.

## `skills/` — installed to `~/.claude/skills/<name>/SKILL.md`

- `termux-doctor/` — always installed (not opt-in). The 9-trap list +
  self-repair playbook for the whole patched-ELF-on-Bionic setup itself.
  Triggered on any symptom (segfault, bad ELF magic, patchelf weirdness).
- `adb-bridge/` — opt-in, installed with `--with-adb-bridge` at install
  time OR `termux-claude-features enable adb-bridge` any time after. Where
  the SAFETY POLICY for the wireless-ADB feature lives (ask before a new
  pairing, never wire screen/input actions into a background hook, remind
  to disconnect after) — `adb-bridge.sh` is just the mechanical half; this
  skill is the judgment half. See its "Security posture" section first.

## `docs/` — staged to `~/.claude/claude-native/docs/`

Every `.md` file here is staged generically (`install.sh` loops over
`docs/*.md`) — adding a new file to this directory needs no install.sh
edit.

- `architecture.md` — this file.
- `claude-code-hooks-reference.md` — distilled, by-topic reference for
  Claude Code hook behavior (event list, per-event output fields,
  `systemMessage` vs `additionalContext`, confirmed `settings.json` keys).
  General-purpose, not Termux-specific — useful for any Claude Code hook
  work, kept here because this repo's own hooks are what forced it to be
  verified this carefully.
- `termux-api-survey.md` — every `termux-*` command surveyed while
  researching what this repo could build: what needs the Termux:API app,
  what was built vs. deliberately deferred vs. rejected, and the
  screen/input/logcat gap that motivated the separate `adb-bridge`
  feature.
- `keybindings-notes.md` — the *why* behind `keybindings.json.template`'s
  rebinds (JSON has no comment syntax to hang this reasoning off of in
  the template itself).

## `notes/` — research log, own reference, not synced anywhere

- `termux-features-research.md` — running log of what's been surveyed/
  discovered across sessions, organized as numbered sections (1 =
  Termux:API command survey, 2 = Claude Code hooks verified facts, 3 =
  keybindings, 4 onward = later feature work: the adb-bridge incident and
  its hybrid script+skill design, the install/uninstall toggle-command
  rethink, this doc's own origin). **Append-only in spirit** — when
  something here turns out wrong, a later section corrects it in place
  rather than silently rewriting history; read chronologically if the
  most-current understanding matters more than the narrative.
- `planned-features-and-seo.md` — not covered by this map; check directly
  if relevant.

## Templates merged into `~/.claude/` (not run — content only)

- `CLAUDE.md.template` — merged into the user's global `~/.claude/CLAUDE.md`
  between `<!-- claude-code-termux-native:begin/end -->` markers by
  `claude_md_upsert` (`lib.sh`). This is the file a live Claude session
  actually reads at the start of every session, in every project — kept
  deliberately minimal (see "Why this lives here, not in CLAUDE.md").
- `keybindings.json.template` — merged BY VALUE (no comment syntax to hang
  markers off) into `~/.claude/keybindings.json` via `keybindings_upsert`,
  tracked in `~/.claude/claude-native/.keybindings-managed.json`.

## The core pattern for adding a new opt-in feature

The enable/disable logic for a toggleable feature lives in ONE place
(`feature-hooks.sh`), called identically by three entry points — nothing
about it lives inside install.sh/uninstall.sh themselves. To add one:

1. Stage the feature's script UNCONDITIONALLY in `stage_scripts()`
   (harmless dormant file until wired). Any skill it needs is ALSO staged
   unconditionally as a source file under `skill-sources/<name>/`.
2. Write the wiring logic (hook in settings.json + copying the skill into
   `~/.claude/skills/`) ONCE as `enable_<feature>`/`disable_<feature>`/
   `<feature>_wired` functions in `feature-hooks.sh`, using the generic
   `hook_upsert_entry`/`hook_remove` helpers there — never hand-rolled jq.
3. Make all three callers share those functions: `install.sh`'s
   `--with-X` flag (`install_<feature>()` becomes a 1-line call),
   `uninstall.sh` (`remove_<feature>_hook()` likewise), and
   `termux-claude-features enable/disable <feature>` (`claude-features.sh`,
   sourcing the STAGED copy of `feature-hooks.sh` since the repo checkout
   may be long gone by the time this runs).
4. `uninstall.sh` removes the new feature's wiring UNCONDITIONALLY (no
   flag) — must be a safe no-op when it was never installed.
5. Add a status line to `doctor.sh` for it, regardless of whether it's
   enabled on this machine.
6. Add a line to `claude-features.sh`'s `cmd_status` — with the feature's
   own one-line description and any safety notes written directly into
   that line (this is what a live Claude session actually reads to decide
   whether/how to suggest the feature — see below).
7. Update `README.md`: a bullet in "Extra features", an entry in the
   numbered "What install.sh does" list, new paths in "Layout after
   install". Guidance there says "use `termux-claude-features`", never
   "re-run install.sh with a different flag", for anything post-install.
8. Update this file (`docs/architecture.md`) — NOT `CLAUDE.md.template` —
   with the new file's role. `CLAUDE.md.template` should not need an edit
   just because a new feature was added; see below for why.

## Why this lives here, not in CLAUDE.md

`CLAUDE.md.template` carries a hard, real token cost: it's merged into
`~/.claude/CLAUDE.md`, which is loaded into **every** Claude Code session
in **every** project on this device, whether or not that session ever
touches this repo. The user's own global CLAUDE.md (outside this repo's
managed block) already enforces a size guard for exactly this reason.

This file and `claude-features.sh`'s `status` output are the two places
that absorb the detail instead:

- **`claude-features.sh status`** is the source of truth for what each
  *toggleable* feature does and any safety notes — not `CLAUDE.md`. This
  is why `CLAUDE.md.template` names the command as a single generic,
  stable bullet instead of one bullet per feature: adding feature #3
  means editing `claude-features.sh`'s output text, never
  `CLAUDE.md.template` again.
- **This file** is where the deeper "how does the whole repo fit
  together" detail lives — staged to `~/.claude/claude-native/docs/`
  specifically so a live session can read it **on demand** (a plain file
  read costs nothing until actually read) instead of it being force-fed
  into every session's context via CLAUDE.md regardless of relevance.

Net effect: `CLAUDE.md.template`'s footprint stays roughly constant as
this repo grows, while the actual amount of documented detail available
to a Claude session working in this repo keeps increasing — it's just
opt-in-by-read rather than paid-for-every-session.
